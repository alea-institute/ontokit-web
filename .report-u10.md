# U10 Auto-save Preference Report

## Outcome

R9 is implemented. Auto-save is invariantly on, users can choose whether the editor shows an immediate manual Save button, and the first successful navigate-away auto-save shows a teaching toast once per browser profile. The amber draft indicator remains unchanged.

## State-model decision

The persisted model now exposes `showManualSaveButton` instead of combining `hideSaveButton` with a separate auto-save toggle. There is no `autoSaveEnabled` field or setter: auto-save is always active, so the stranded state "manual saving only + hidden Save button" cannot be represented at the state level.

The same persisted store tracks `hasSeenAutoSaveToast`. A successful auto-origin flush claims the teaching toast; explicit Save and Retry actions use the manual origin and do not consume it. The claim uses Web Locks plus a dedicated localStorage marker to prevent two open tabs from both teaching. Browsers without Web Locks fall back to the persisted/in-memory claim.

## Migration

`ontokit-editor-preferences` is now version 1.

- Legacy `hideSaveButton: true` migrates to `showManualSaveButton: false`. Auto-save remains on, so this is a safe auto-save-only state.
- Legacy `hideSaveButton: false` migrates to `showManualSaveButton: true`, preserving the visible-button behavior.
- A persisted blob that predates `hideSaveButton` also receives `showManualSaveButton: true`, matching the old default.
- The obsolete `hideSaveButton` property is removed from the hydrated state.
- Existing profiles receive `hasSeenAutoSaveToast: false` unless they already have the versioned field, so they see the teaching toast on their first successful auto-save after upgrading.
